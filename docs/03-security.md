# Безопасность

## Что защищаем
- Финансы семьи, документы, медданные детей, фото, переписка-обсуждения.
- Сам доступ к семье: нельзя тихо добавить чужого человека или выгнать админа.

## От кого
| Угроза | Пример |
|---|---|
| Посторонний в интернете | перебор паролей, подбор ID, кривые запросы к API |
| Украденный пароль | фишинг, утечка с другого сайта |
| Украденный/разблокированный телефон | ребёнок или чужой человек открыл приложение |
| Скомпрометированный аккаунт одного админа | попытка добавить себе сообщника, удалить второго админа, удалить данные |
| Участник семьи с меньшими правами | ребёнок пытается увидеть финансы, взрослый — чужие личные операции |
| Сервер/хостинг | утечка бэкапа или БД (защищаемся сейфом с E2E, этап 6) |

## Модель угроз (STRIDE) и меры

| STRIDE | Риск | Мера | Где проверено |
|---|---|---|---|
| **S**poofing | вход с чужим паролем | обязательная 2FA (TOTP), RLS требует `aal2` на всё семейное | `010_families`, `020_approvals` (aal1 → пусто/ошибка), `AppModelTests` |
| S | подделка `created_by` / `owner_id` | колонки не в `GRANT`, значение берётся из `auth.uid()` | `030_budget`, `040_attachments` |
| **T**ampering | изменить роль, family_id, сумму в базе | column-level grants, триггер пересчитывает `amount_base_minor`, иммутабельные поля | `010`, `030` |
| T | правка журнала аудита | нет прав + триггер append-only даже для владельца таблицы | `050_audit` |
| **R**epudiation | «я этого не делал» | `audit_log` с актором для критичных действий | `050_audit` |
| **I**nformation disclosure | чужая семья видит данные | RLS по членству, `anon` не имеет прав ни на что | `001_security_baseline`, `010` |
| I | ребёнок/гость видит финансы | финансы только `adult+` | `030` |
| I | админ видит личную операцию взрослого | `is_private` → видит только автор; чек тоже | `030`, `040` |
| I | перебор ID приглашений/запросов | единая ошибка «не найдено» без различия причин | `020` |
| I | геоданные в фото чека | перекодирование JPEG на устройстве удаляет EXIF/GPS | `ReceiptProcessorTests` |
| I | снимок экрана в переключателе приложений | `PrivacyShield` закрывает контент в неактивном состоянии | `AppLockTests` |
| I | ошибки сервера в UI | `mapError` показывает только общие сообщения | `ConfigurationTests` |
| **D**oS | спам запросами/семьями | лимиты в RPC (≤5 семей, ≤50 ожидающих запросов), rate limit GoTrue | `010`, конфиг |
| **E**levation of privilege | админ в одиночку добавляет/удаляет людей при двух админах | «четыре глаза»: `request_action` → `approve_request` другим админом | `020` |
| E | последний админ понижен/удалён | проверка инварианта в `execute_approval`, `leave_family` | `010`, `020` |
| E | вызов внутренних функций | хелперы в схеме `private` (не в API), `EXECUTE` выдан только нужным для RLS | `001` |
| E | `SECURITY DEFINER` + подмена `search_path` | у всех definer-функций `set search_path = ''` | `001` |

## Аутентификация
- Пароль ≥ 12 символов, строчные + заглавные + цифры (сервер и клиент — `PasswordPolicy`).
- Подтверждение email обязательно; смена пароля требует недавнего входа.
- Ротация refresh-токенов, выход — сразу на всех устройствах (`signOut(scope: .global)`).
- TOTP: QR-код или «Добавить в Пароли» (встроенный в iOS генератор кодов), автоподстановка кода.
- Сессия хранится в Keychain (по умолчанию в supabase-swift).
- Face ID / код-пароль устройства при запуске и при возврате через 30 секунд.
- Sign in with Apple и passkeys — после активации Apple Developer.

## Четыре глаза
Критичные действия: пригласить, удалить, сменить роль, удалить семью.

- 1 админ — выполняется сразу (спросить некого).
- 2+ админа — создаётся запрос, выполнить может **только другой** админ, срок 7 дней.
- Важное следствие: скомпрометированный аккаунт одного админа не может ни добавить постороннего, ни выгнать второго админа.

## Сейф (этап 6, план)
- Ключи генерируются на устройстве. Приватный ключ лежит в Keychain/Secure Enclave и защищён Face ID.
- Документ шифруется случайным ключом (AES-GCM), а этот ключ — публичными ключами тех, кому открыт доступ.
- Сервер хранит только шифротекст. Восстановление — через бумажный ключ восстановления или второго админа.

## Пентест и проверки (план)
- Каждый PR: pgTAP (RLS, роли, подделки), unit/UI-тесты, gitleaks, Semgrep.
- Перед TestFlight: прогон OWASP MASVS (L2), ручные проверки API через Burp/ZAP (IDOR, mass assignment, обход RLS через RPC, фаззинг), MobSF для сборки, проверка заголовков и TLS сервера.
- Найденные проблемы оформляются тестом, который сначала падает.

## Итоговый обзор безопасности (этап 1, после модулей до «Заметок»)

Проверено вручную по коду и миграциям, плюс автоматические проверки в CI (pgTAP, gitleaks по всей истории, Semgrep, Actions закреплены на SHA).

**Найдено и исправлено (каждое — с тестом, сначала падавшим):**
1. **Запрос уже не-админа можно было подтвердить.** Админ создал запрос и потерял роль (или был взломан и разжалован); второй админ подтверждал, и запрос выполнялся со старыми правами. Теперь `approve_request` требует, чтобы автор всё ещё был админом (`20261002000900_approval_requester_check.sql`, тест `055_review_findings`).
2. **Блокировка Face ID блокировала владельца навсегда**, если на iPhone нет код-пароля. Теперь в этом случае замок не включается, а в настройках видно предупреждение, что он не действует (`AppLockTests`).
3. **Сессия в Keychain** хранилась с доступом, который переносится на другое устройство через зашифрованную резервную копию. Теперь `AfterFirstUnlockThisDeviceOnly` без синхронизации с iCloud (`DeviceOnlyKeychainStorage`).
4. **Защита от ошибки в будущем:** тест, что у `authenticated` нет прав INSERT/UPDATE на таблицу целиком (только по колонкам), то есть нельзя случайно открыть запись в служебные поля.

**Проверено и в порядке:** RLS и явные GRANT на всех таблицах; все SECURITY DEFINER с `search_path = ''`; `anon` без прав; внутренние функции вне API; журнал аудита неизменяем; изоляция семей, ролей и личных записей (в том числе чеки, цели, заметки); приглашения привязаны к подтверждённому email; deep link работает через PKCE (перехват кода другим приложением бесполезен без локального verifier); в коде приложения нет логирования; секретов в репозитории нет.

**Принятые риски и заметки:**
- `NSAllowsLocalNetworking` в Info.plist включён для всех сборок (нужен для локальной разработки по http). В коде `SupabaseClientFactory` в Release всё равно отклоняет не-https. Перед релизом вынести в Debug-конфигурацию.
- Регистрация открыта (нужна приглашённым). Лимиты запросов и защита от перебора кодов TOTP задаются в настройках Auth сервера: на проде проверить, а не полагаться на локальный `config.toml`.
- Custom URL scheme `familyapp://` вместо universal links: с PKCE безопасно, но universal links надёжнее (после появления домена).
- Свободные файлы в Storage (загружены, но не привязаны) могут копиться у взрослых участников: нужна периодическая очистка.
- Не проверено на реальном Supabase: можно ли при уже подтверждённом факторе добавить второй фактор на уровне aal1. Проверить при пентесте; при необходимости закрыть правилом на стороне Auth.

## Ещё не сделано (честно)
- Certificate pinning (решим вместе с выбором хостинга).
- Universal links вместо custom scheme; перенос `NSAllowsLocalNetworking` только в Debug.
- Детект jailbreak (низкий приоритет, легко обходится).
- Очистка «осиротевших» файлов в Storage (scheduled job).
- Автоматические курсы валют (сейчас курс вводится вручную).
